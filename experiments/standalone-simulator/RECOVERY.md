# 2026-09-27 写锁故障恢复

上一轮在 147,276 场完成后因 SQLite 写锁导致 worker 退出，遗留一个已经结束战斗但未提交的租约。其原始 `StandaloneCompleted` 行、独立请求文件与任务一致，在一次性测试库中已通过 `Store.finish` 校验；恢复提交不重打战斗、不补造耗时。旧长跑仍属于中断，不能补记为 24 小时通过。

本次只修改采集与验收控制，不修改冻结宿主、教师搜索预算或游戏规则：

- 写锁等待使用 250 ms SQLite 等待与随机退避，保留 90 秒总等待预算；只重试尚未取得事务的 BEGIN，不重放事务体或提交。
- 每个 runtime 保存经 fsync 的领取凭据及原始结果；提交后才移除凭据。提交已成功但移除前中断时，对照原租约的 attempts 精确去重。
- pool 持有数据库池锁，并确认全部 runtime 的 collector 锁释放后，才能恢复凭据。无结果的已领取任务记录 interrupted 尝试；有结果的任务提交原结果。过期结果不覆盖新租约。
- 在线备份复制完成后即释放来源 WAL 读快照，之后再检查备份副本。
- 排空失败仍保存阶段报告和原始异常，不能将遗留租约问题覆盖为看似完成。

验证包括真实 SQLite 锁竞争、提交后中断、重复恢复、活跃 owner 拒绝恢复、旧租约拒绝覆盖、无效标签拦截、在线备份期间 WAL 截断，以及 24 进程 4,800 合成任务压力测试。合成数据与真实采集严格分开，这类测试不计入战斗一致性数量。
