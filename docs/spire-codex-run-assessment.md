# 真实 `.run` 构筑采集

用户已确认：以真实战前卡组与遗物组合为基础，暂停随机构筑变异；遗物计数可以随机。最新v4规则移除影响最大生命的遗物和用户指定的5种遗物，统一70/70开战；核实过的获得效果不再重复执行，保留其遗物和已有卡牌变化。具体清单见 [遗物规则](unadapted-relics-20260906.md)。实现不还原真人的历史计数，而是在已验证的合法范围内可复现采样。同一输入的四个战斗种子保持计数一致。

## 数据源

目标采集改为 `source_floor_window_v1`：每个已接受的战前构筑，测试同一份 `.run` 中来源楼层 f−2 到 f+2 实际出现的怪物编组，包含本层、保留原版编组、不跨幕。按楼层编号取范围；商店、营火等非战斗层不会补成额外战斗。相邻层不要求其自身构筑可还原，怪物必须在当前原生目录中；未适配事件战斗保留跳过记录。同一构筑在多个楼层或来源中出现时取目标并集，每组仍用原四个种子，不重复采已完成任务。

已采集结果全部保留。旧整幕队列中超出窗口的未完成任务改为 `excluded_target`，不删除任务或尝试；新的真实来源若重新覆盖该目标，只恢复对应未完成任务，保留原计数。`target_origins` 记录构筑、来源、来源楼层、目标楼层和编组；`job_scope_changes` 记录退出和恢复。输入规则仍为 `relic_pickup_normalization_v4`，老师、构筑身份、遗物计数和掉血标签公式均不变。`tools.migrate_target_scope` 先预览，应用时需要停止池及控制器、持有全部工作锁，制作 SQLite 一致性备份并核对旧结果、输入、attempts 和原始来源未变。

[Spire Codex 开发者文档](https://spire-codex.com/developers)说明公开 JSONL 导出和限流；[官方源码 exports.py](https://github.com/ptrlrd/spire-codex/blob/main/backend/app/routers/exports.py)给出实际路由 `/api/exports/runs`、gzip 内容和 `X-Next-Cursor`。文档所列 `/api/runs/export` 在本次验证中返回 404，实际路由已在本机成功下载。

客户端使用说明用途的 User-Agent，每页 1,000 份、至少间隔 31 秒，遇到 429 尊重 Retry-After。submitted-at 时间窗在分页中保持不变，仅在完整页校验和导入结束后保存下一游标。临时网络故障退避；下载截断、校验失败和来源内容冲突不推进游标。原始公开页写入缓存，筛选单人、静默、A10、标准模式、schema 10、游戏 v0.111.0；不按真人胜负或掉血筛选。

## 还原与拒绝边界

从原始静默牌组加进阶之灾开始，按实际楼层处理获得牌、移除、变牌、升级、降级、附魔记录，以及遗物获得顺序和先古来源。战前快照在该层变化之前，因此战后奖励不会提前进入战斗。

升级只有卡牌 ID、缺少实例 ID；同一楼层的不同变化列表也没有统一时序。导入器保留一致的多种解释，最终与 `.run` 最后牌组、升级、获得楼层和遗物顺序核对。只有各解释都一致的战前卡牌多重集可用；超过歧义上限、记录不完整或终局无法对上的局有明确拒绝原因。

附魔现按每张牌保存 ID、数值与升级次数，加入构筑身份、原生请求、开战状态校验与模型特征。现成附魔牌获得记录和重复的相同附魔历史不会二次施加效果；不同历史解释仍须通过最终牌组核对。

以下战斗来源仍会跳过、不进入队列：未知或未适配的卡牌持久字段（静默范围内的藏宝图、探寻、愧疚、疯狂科学等已按 [特殊卡牌与持久状态](card-state.md) 还原）、同层事件与战斗混合而不能确定战前边界、海玻璃和玩具盒等未适配遗物保存字段，以及棱彩宝石、万花筒等仍禁止的遗物。最大生命遗物及[明确移除的遗物](unadapted-relics-20260906.md)从输入删除后保留其余构筑，不再因药瓶皮套、蜥蜴尾巴等身份整份跳过；静默猎手的欧罗巴斯之触替换已适配，其他未知替换和效果仍拒绝。当前解析对同层不同类别操作枚举顺序，不对类别内部交错操作穷举；无法核对的复杂局会拒绝，可能损失覆盖率。

现有原生接口支持 `addWithoutObtainedEffects`。已核实的一次性遗物（例如Pomander、砥石、War Paint、黄金珍珠、铅质镇纸等）直接装入，不重复执行已记录的升级、删牌和奖励。仍然带有未知持久字段的遗物不会因此自动放行。音叉 SkillsPlayed 的 0–9 范围来自当前 0.111.0 原版 IL，非零输入经原生对战验收；其他已适配计数范围见 [counter-state.md](counter-state.md)。

## 保存与训练隔离

生命标签按 `initialHp - finalHp` 记录，起始仍统一70/70。当前 `native_max_hp_costs_v2` 允许两种已核实的原版机制：两个咬人卷轴编组的纸割在攻击命中并造成未格挡伤害时扣除2点最大生命；起始牌含BRIGHTEST_FLAME时，每次打出该牌扣除2点最大生命，升级不改变该成本。下降必须匹配2的倍数或原版最低1点钳制，其他最大生命变化仍拒绝；实际开战构筑仍完整核对。最大生命变化不额外加权到掉血标签中，原生 `finalMaxHp` 和导出的 `final_max_hp` 单独保留，数据页战后血量使用实际战后上限。这不改变最大生命遗物的移除规则，也不修改已完成的旧标签。原生及恢复证据见 `evidence/overnight-retry-20260907/`。

- `builds/jobs/attempts`：输入、同幕目标、固定老师、战斗种子及原生终局。
- `source_runs`：完整来源 JSON、URL、导入版本、规范化游戏内容 SHA-256、接受/拒绝报告。规范化摘要忽略 shared/export 接口增添的 run_hash、username、has_replay、damage、player_index 展示字段；原文仍保留，下载页另有逐字节摘要。
- `source_equivalences`：`spire_codex_metadata_v2` 另兼容两个已核实的顶层附加字段is_beta和_spirecodex_damage。共享接口根据build_id派生前者，并把后者改写为damage；build_id及实际游戏历史仍严格比较。读取旧来源先按旧/新算法核验原文摘要，再比较规范化内容；不改写旧source_runs或sha256，等价的新完整payload另存审计。未知差异仍拒绝，不能通过忽略任意字段推进游标。核对证据见 `evidence/source-content-conflict-20260906/`。
- `build_origins`：每个输入对应的源局、楼层、原目标和计数采样种子。不同局出现相同输入时，原生任务去重，所有来源保留。

新库与旧随机构筑库隔离。附魔观察协议2使用 `collection-real-runs-v2.sqlite`，旧真实局库原样保留。当前 `relic_pickup_normalization_v4` 继续扩充同一老师的输入：显式重评v2/v3源局，保留全部旧任务与终局，在 `source_import_history` 保存每一版旧报告；新来源审计区分移除的最大生命遗物和用户指定遗物。先古来源仍完整保存，同时核对移除前的真实持有关系，不能因归一化伪造先古历史。训练取固定快照，按源局和共享输入形成的连通组划分数据；没有足够独立留出组就拒绝训练。当前只采集，不覆盖旧模型。后续需要报告来源筛选、首层偏重、未支持持久状态及上传者分布造成的覆盖限制；标准化后的构筑不是完整真人原始构筑。

## 本次验证

初批 16 份匹配原始局中，9 份贡献了 56 个可接受战前楼层，去重后 55 套输入，4,536 个同幕独立任务。之后公开分页继续扩展，这是初批数字而非最终样本量。

原生验收四场：第一幕 13 牌Pomander构筑 70→70；第二幕 20 牌、音叉计数 0 构筑 70→59；第一幕 15 牌含事件牌构筑 70→70；19 牌、音叉计数 1 构筑 70→70。各场实际初始卡组、升级、遗物顺序、计数及完整终局均通过校验。这验证输入链路，不是对所有卡牌或怪物的完整求解器正确性证明。

Linux 采集/来源/锁/恢复相关测试通过，租用环境缺少 PyTorch，四项模型相关测试跳过。本次没有训练新模型。随机生成器、父代选择、seed/evolve 及旧 collect_rounds 已删除；历史 Build 元数据和旧 configs/v1.json 仅用于兼容旧数据。
